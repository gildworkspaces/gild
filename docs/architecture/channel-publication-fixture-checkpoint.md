# Channel publication fixture correction after `b234a4f`

The channel first-paint gate previously captured anonymous HTML after an HTTP-200 publication response without checking its `published` boolean. The actual publisher can decline when its prepared inputs are Pending or their fence changes. The fixture now uses the existing navigation preparation behavior through one shared helper: retry a declined result within a bounded deadline and capture only after successful publication. No foreground route, product source, privacy/cache policy or browser performance threshold changes.

Hosted API failure on `b234a4f` was `published HTML includes messages`. One unchanged-assertion local diagnostic passed, so the specific hosted race/cause is unproven. That diagnostic captured an earlier declined preparation and a final successful publication; it supports handling the explicit response contract, not a claim that production rendering was fixed here.

`node scripts/channel-fast-web.mjs --declined-publication` deliberately asks the actual fixture publisher for a nonpublishable route once and verifies its real `published:false`, then prepares the actual channel route. The complete original SSR/messages/participants, no-JavaScript public HTML, WebSocket cursor, 300ms first-paint budget, 50ms warm participant budget, CLS and private-reader parity assertions pass (`.tmp/channel-publication-challenge.log`). This is a fixture readiness challenge, not a reproduction of a concurrent input-version race.

An isolated copy removes the helper acceptance condition while leaving product source and all assertions unchanged. The same challenge fails the named `channel document capture requires successful current-route publication` assertion before HTML capture (`.tmp/channel-publication-removal.log`); no import, timeout or setup failure is counted. Productive files remain byte-identical during that proof. The ordinary `bun run test:channel:fast` gate is recorded separately in `.tmp/channel-publication-restored.log`.
