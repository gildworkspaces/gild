# Webhooks and event streams

Gild never hosts agent runtimes. Repository owners manage hooks under Settings → Webhooks or `/api/v1/repos/{owner}/{repo}/hooks`; organization owners/admins use `/api/v1/orgs/{org}/hooks`. Both require `hooks` scope. Supply GitHub's `config.url`, `config.content_type` (`json` or `form`), `config.secret`, `events`, and `active`. Secrets are stored privately in the event Durable Object and never returned. A create sends a ping.

Deliveries carry `X-Gild-Event`, a UUID `X-Gild-Delivery`, a Unix-seconds `X-Gild-Timestamp`, and HMAC-SHA256 over `timestamp + "." + exact request bytes` in `X-Hub-Signature-256` plus `X-Gild-Signature-256`. Receivers must compare signatures in constant time and reject timestamps more than **5 minutes** from their clock (in either direction). Persist delivery UUIDs to reject duplicates within that window. Retried attempts retain the delivery UUID and get a new signed timestamp. These headers use GitHub-style names but the signed input includes the timestamp, unlike a body-only GitHub signature. Manual redelivery creates a fresh UUID and retains the event payload. Queue retries wait 5, 10, 20, 40, 80, 160, and 320 seconds, with eight attempts maximum; 10 consecutive failed attempts disable the hook, expose a notice in Settings, and append `webhook_disabled`. Re-enabling resets the count. The most recent 100 deliveries include request headers/body, bounded response body, status and duration. Receiver responses must be 2xx; redirects are failures.

Receivers must use public HTTP(S) destinations. Every A/AAAA answer is checked, and the connection pins a checked address with TLS verifying the original hostname. Private, loopback, link-local, reserved and tunnel address ranges are rejected, including alternate numeric URL forms. Total delivery timeout is 10 seconds. Cloudflare's outbound TCP API currently blocks Cloudflare destinations: receivers behind Cloudflare cannot receive through this pinned transport. Their delivery log records the failure. Deploying a public egress proxy would require a separate infrastructure decision; the guard does not fall back to a DNS-rebinding-prone fetch.

`GET /api/v1/events?repos=owner/repo&since=123&wait=20000` needs `repo:read`. It returns `{events,cursor}`; each event includes its durable cursor and the same payload delivered to hooks. Omit `since` to start at the current tail. Persist the returned cursor even when the page is empty; unrelated events advance the cursor without being exposed. A token's repository allow-list and the shared repository read check both apply to every selected repository, including unrestricted tokens. Omitted `repos` selects only readable repositories. Viewer filtering is not cached. Hooks store their creator and check their current organization/writer and repository read access before every attempt, including manual redelivery. Revocation disables the hook with a reason; organization hooks never deliver a private repository the creator cannot read. Old hooks without a recorded creator are disabled and must be recreated. Private join requests are restricted to their sponsor. Streams retain events across worker restarts. `Accept: text/event-stream` returns SSE frames with `id`, named events and JSON data; reconnect after each bounded 20-second response with `Last-Event-ID` (or `since`). A final `cursor` frame advances past filtered events.

```
gild events tail --repo owner/repo
gild events tail --repo owner/repo --since 123
gild events tail --agent codex --repo owner/repo
```

The CLI prints one JSON envelope per event, uses bounded long-polling, and resumes from each returned cursor. `--once` reads a page and prints its cursor to stderr.

Git writes include event records in the winning metadata commit. Repo-index, Actions and D1 join-request outboxes retry through a single `emit(event)` into the durable event log; event IDs deduplicate acknowledgement/crash replay. Git pushes schedule indexed history/diff and cqx work in the background. Hash-derived diffs and cqx reports are cached by hashes/build, never cloned on an event read. Hook administration, deliveries and per-viewer streams are `no-store`.

Ava rollout: create Cloudflare Queues **gild-webhooks**, bound as **WEBHOOKS**, and **gild-webhooks-dead**, with a consumer for both; apply D1 migration **0010_event_outbox.sql**, create SQLite DO **ForgeEvents** bound as **EVENTS**, and deploy the Worker with queue consumer and minute cron. The cron drains D1 source outboxes; existing repo/Actions alarms drain their own outboxes. Local tests use Wrangler/Miniflare queues and generated fixture credentials. No queue or deployment is created by the implementation PR.

Delivery logs use GitHub numeric `id` values and UUID `guid` values. The UUID is sent in `X-Gild-Delivery`; retries retain it, and manual redelivery gets a new one. `request.payload` contains the parsed event object; `request.wire` preserves the exact bytes signed and sent (including form encoding). Numeric IDs are never reused after log retention or hook deletion.

The primary consumer dead-letters messages after seven queue retries; the dead-letter consumer persists `failed` and the reason in the existing delivery list before acknowledgement. Lease contention publishes a new message with a 15-second delay and acknowledges the colliding message, consuming no retry. Alarms run while deliveries remain unfinished and sweep `queued=1`/expired sending rows after one hour, beyond the normal eight-attempt backoff (635 seconds plus up to 80 seconds of delivery time). Uncertain queue sends may duplicate messages; durable delivery state/leases prevent concurrent effects.

Queue behavior follows [Cloudflare dead-letter configuration](https://developers.cloudflare.com/queues/configuration/dead-letter-queues/) and [delayed sends and acknowledgement](https://developers.cloudflare.com/queues/configuration/batching-retries/).

V1 hub sizing decision: retain the single `forge-v1` event log for this pre-deployment round. The real local Workerd/SQLite fixture accepted **200 sequential `emit` RPCs in 2.523 s (79.26 events/s, 12.62 ms/event)**, after exercising queue delivery, cursor resume and long-poll/SSE. This is a local burst measurement, not a production capacity guarantee or a traffic claim. Use **10 events/s** as the initial pilot sizing budget, giving 7.9× headroom against that measured sequential rate; do not roll out a broader workload on this evidence. Sharding requires a vector cursor across owners instead of the currently documented single numeric cursor. Implement per-owner shards before exceeding that pilot budget or if production emit latency exceeds 100 ms at p95. A multi-owner long-poll/fan-out capacity test is still needed before a larger rollout. Keeping one log now avoids changing the cursor contract during this security repair; repository access is checked per caller independently of log placement. Reproduce with `bun run test:events`; `.tmp/event-hub-timings.json` records the measurement.
